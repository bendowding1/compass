## Problem Statement

Internal project delivery is chaotic because there is no single standard shape for a project. Information lives in email, SharePoint, Jira, group chats, and people's heads. The Jira the company already pays for is too large and misconfigured for any one team to get what it needs. The deeper cause is not a missing tool, it is the absence of an agreed, enforced standard. Every project is structured slightly differently, so nobody can switch context, find information, or trust a deadline.

Compass is an internal portal giving PMs, developers, testers, and deployment a single, standardized project view, built around the one unit everything actually revolves around: the milestone (release).

## Demand Evidence

Honest read: this is sponsor-driven, not yet user-pulled.

- The strongest concrete signal is organizational: the company is spending real money on project-management training and "concepts" to restructure how projects run. Budget is already moving. A funded sponsor is the single biggest asset an internal project can have.
- The one named end user who wants it is the engineering manager (the requester). That is real demand, but it is manager-pull (visibility), not yet demonstrated bottom-up pull from devs, testers, or deployment.
- Real IC pain exists and was described concretely: developers cannot find requirements scattered across email and SharePoint, and developers get blamed when issues surface mid-build that "should have been known at the start."
- No shadow workaround, no unprompted "when can we have this," and no specific named IC champion was identified yet. Closing that gap is the priority before or alongside building (see The Assignment).

Risk flagged: the manager-dashboard tax. A view the manager wants, fed by data that ICs must enter but get nothing from, goes stale within weeks and loses trust. v1 must give each role something they personally want, or the data must arrive without manual entry.

## Status Quo

Concrete walkthrough (PM, the highest-pain coordinating role):

- PM gathers requirements via emails, meetings, and SharePoint documents. "A big mess."
- PM hands off to a developer. Developer complains about the mess and where to find the info.
- PM wants the dev to build a plan with dates. PM sometimes changes these and the change history is lost.
- Developers build, but the PM does not know what they are working on or when it will land.
- Developers hit problems mid-build, raise them, and the PM reacts aggressively ("you should have known at the start").
- Every project is structured differently, so context-switching and shared visibility are hard.

Context that shapes the design: the company ships hardware and software to customers in the field. "Test" means testing builds on real devices. "Deploy" means physical field installation on customer devices. This is not a pure SaaS pipeline.

## The Model (milestone-centric)

Corrected during design review, after the user reviewed the first mockup and spotted that a single linear timeline cannot represent how they actually work. The accurate model:

- **Project**: the long-lived container. It belongs to a **Customer** (chosen from a predefined list of current customers, so you always know who the project is for), carries a **lifecycle status** of **NPD** (New Product Development) / **Sustaining** / **Closed**, names a **Responsible** person per function, and holds project-level docs and a stream of milestones.
- **Milestone (Release)**: the central, repeating unit. **Nothing happens outside a milestone.** Each one runs the fixed cycle **Requirements → Build → Test → Deploy** and ends in a delivered release. A project is a sequence of milestones over time (monthly, or whenever scope is ready).
- **Responsible roles** (named per project): **PM, Development, Test, Deploy, Customer Care.** So anyone on the page knows who to talk to. The middle three map to the milestone steps they own; Customer Care holds the post-deploy relationship; PM owns the whole.

The rigidity (premise 2) now lives on the milestone: every milestone is the same four-step shape, on every project. The project view aggregates the stream. Sign-off is folded into the Requirements step (the gate to leave Requirements); if it must be its own step, that is a one-line change. [OPEN: confirm sign-off placement.]

## Target User & Narrowest Wedge

Primary user for v1: the PM (and the EM), the coordinating roles that assemble project status by hand today. Secondary beneficiary on day one: the developer who cannot find the info, solved by the doc hub.

Narrowest wedge (chosen): a rigid, same-shape-every-time **project page**, milestone-centric, containing:

1. **Header**: project name, **Customer** (from the predefined list), **lifecycle status** (NPD / Sustaining / Closed), and a quiet "updated by [name] on [date]" stamp.
2. **Milestones** (the main content): the stream of milestones, each a card carrying its own **Requirements → Build → Test → Deploy** tracker, a status, and a target/actual delivery date. The current milestone is highlighted.
3. **Responsible** panel: the five named roles (PM, Development, Test, Deploy, Customer Care).
4. **Project docs**: one canonical place linking every spec and document. Highest-value, lowest-risk piece, links do not go stale. Directly kills "the developer cannot find the info."

Honest scope of v1: milestone step-status and dates are PM-entered, not connected to live dev progress (the dev board is a later phase). v1's value is "one understandable, standardized page per project, with the docs and the people," NOT "accurate live status." These two must never be confused.

Change history: v1 records a lightweight "changed by and on" stamp per milestone, cheap, and it directly addresses the named pain of milestone changes vanishing. A full audit log is deferred to phase 2.

## Constraints

- Microsoft / M365 shop: docs live in SharePoint, SSO available.
- Hardware plus software product, field deployment to customer devices.
- Pre-product, idea and scoping stage. No code yet.
- A PM-methodology transformation (training, new concepts) is in flight. The standard is still being defined. The tool encodes that standard, so the tool is downstream of the methodology work.

## Premises (all confirmed by the user)

1. The root problem is the missing standard, not the missing tool. Compass exists to encode and enforce one project shape.
2. The standard must be rigid, not configurable. Configurability is what made Jira a mess. "My project is special" is not allowed. The rigidity is the product.
3. Adoption is earned, not mandated. Ship a visibly better shared place first, then retire SharePoint, email, and chat for project info.
4. The first slice is the milestone-centric project page: header (customer, lifecycle, name), the milestone stream (each running Requirements → Build → Test → Deploy), the Responsible roles, and the doc hub, with eyes open that v1 step-status is PM-entered, not live.
5. Long term, Compass must own the handoffs (build to test to deploy) inside the tool, or it stays a pretty dashboard on the same chaos. v1 defers this, but the design assumes it is coming.

## Approaches Considered

### Approach A: Thin custom build (CHOSEN)
Build the smallest real web app: one project equals one page on a fixed template (header with customer + lifecycle status, the milestone stream with each milestone's Requirements → Build → Test → Deploy tracker, the Responsible roles, and a structured docs-links section). PM edits, everyone reads. No dev board, no integrations yet. Model the project + milestone as a lifecycle object from day one so phase 2 bolts on instead of requiring a rewrite.
- Effort: M (human ~3-4 weeks to a polished v1, CC-assisted ~3-5 days to a working v1).
- Risk: Low.
- Pros: live and visibly better in weeks, respects the mandate to build, doc-hub value lands day one, grows into the dev board later.
- Cons: v1 step-status is PM-typed, not live. You own the build and the bugs.
- Reuses: company SSO, existing SharePoint doc storage (link, do not replace).

### Approach B: Schema-first full spine
Model the entire lifecycle up front (project, milestones, steps, releases, test results, deployment), then build only the project page first. Rigidity enforced at the data layer.
- Effort: L (human ~6-10 weeks, CC-assisted ~1-2 weeks).
- Risk: Med.
- Pros: zero rework when adding the dev board and handoffs, rigidity is structural not cosmetic, best long-term trajectory.
- Cons: slower to first value, designing for an unvalidated future (premature-architecture trap).
- Reuses: SSO, doc links.

### Approach C: Rigid page on the M365 stack you already own
Build the standardized, locked project page in Power Apps / SharePoint Lists already paid for, where the docs already live. Centrally lock the template to keep it rigid.
- Effort: S (human ~1-2 weeks, CC-assisted ~2-3 days, mostly config not code).
- Risk: Low-Med.
- Pros: fastest path to a live, visibly better place, tests the real risk (adoption) for almost nothing, docs already live there.
- Cons: low-code ceiling on UX and rigor, governance burden to stop config drift, may force a later migration.
- Reuses: M365 / Power Platform, SharePoint, SSO.

## Recommended Approach

Approach A, thin custom build, with one discipline grafted from B: model the project and milestone as a lifecycle object from day one, even though v1 only surfaces the project page. This keeps phase 2 (dev board) and phase 3 (handoff ownership) additive rather than a rewrite, and avoids the dead-end dashboard.

v1 data model (the lifecycle object, minimal):
- **Customer**: id, name. A predefined, admin-maintained list. A Project belongs to one Customer.
- **Project**: id, name, customer_id, lifecycle_status (enum: NPD | Sustaining | Closed), created_at, updated_at, updated_by.
- **ProjectRole**: project_id, role (enum: PM | Development | Test | Deploy | CustomerCare), person. Five fixed rows per project (the Responsible set).
- **Milestone (Release)**: id, project_id, name, target_date, actual_date (nullable), changed_by, changed_at. Each milestone owns the four fixed steps Requirements / Build / Test / Deploy, each step with a status (upcoming | current | done) and an optional date.
- **DocLink**: id, project_id, label, url (raw SharePoint URL), added_by.
- Deferred, modeled-but-not-built in v1: per-milestone scope items / features, test results, deployment records. They hang off a Milestone, so phase 2 is additive.

A Project belongs to one Customer, has five ProjectRoles, many Milestones, and many DocLinks. Each Milestone owns its four steps. That is the whole v1 schema. (These are the conceptual entities; v1 stores each project as a single JSON document, not relational tables — see the Engineering Plan below and the linked implementation plan.)

Effort (recommended hybrid): the lifecycle-object graft from B is cheap at this scale, a handful of entities, so Approach A's estimate holds and does not creep toward B's 1-2 weeks. The 3-5 day CC-assisted figure is BUILD-ONLY (app shell, the milestone-centric page, customer + responsible + docs, Entra SSO with read-for-all / edit-for-PM). It is gated behind The Assignment (the mock validation) and an agreed page shape. Read it as "about a week of build once the shape is agreed and the mock lands," not a week from today.

Non-negotiable design rules (from the premises):

- The project + milestone template is rigid. One shape. No per-project configuration.
- v1 is honest about manual status. Surface a "last updated by [name] on [date]" stamp so nobody mistakes typed step-status for live truth.
- The architecture assumes the seams (build, test, deploy) become live Compass objects later. Do not paint into a PM-only corner.

## Design (v1 project page)

Current mockup: `compass-pm-page-mockup-v3.html` (project folder; copy under `~/.gstack/projects/compass/designs/pm-project-page-20260625/`). Hand-built HTML (the AI generator needs an OpenAI key, not configured). Reviewed via /plan-design-review on 2026-06-25, then corrected to the milestone-centric model on 2026-06-26 after the user spotted the linear-timeline flaw in the first mockup.

Type: App UI, not a marketing page. Calm surface hierarchy, dense but readable, minimal chrome.

Information hierarchy (what the user sees, in order):
1. Project name; the **Customer** chip and the **lifecycle status** (NPD / Sustaining / Closed) as a three-way control; the quiet "updated by [name] on [date]" stamp.
2. **Milestones** (the main content): a vertical stream of milestone cards, each carrying its own four-step Requirements → Build → Test → Deploy tracker, a status chip, and a delivery date. The current milestone is highlighted at the top.
3. Right rail: the **Responsible** panel (PM, Development, Test, Deploy, Customer Care, named) and **Project docs**.

Visual identity (the "not SharePoint" rules):
- One restrained accent (deep teal), near-black on warm white, hairline dividers, generous whitespace. No card mosaic, no gradients, no icons-in-circles, nothing centered.
- Typography decision: do NOT ship system-ui / Segoe UI. It is the SharePoint and M365 system font, so using it makes Compass look like another Microsoft page and undercuts "visibly better." Pick a distinctive display typeface (Geist, General Sans, or a licensed grotesk) for the project name and section headers. An adoption lever, not polish.

Empty state (the most important screen, build it first):
- A brand-new project is NOT "No items found." It shows: lifecycle set to NPD; **Customer = "Select customer"** (an obvious required pick); the **Responsible** roles listed with PM set and the other four showing "Assign" (so the fixed role set is visible and you can see who is missing); and a Milestones area that states the rule "nothing happens outside a milestone" with one action: **Create the first milestone.** Even empty, the project is more organized than a blank SharePoint page. This is the adoption argument made visible.

Interaction states:
```
STATE         | MILESTONE STREAM                                  | USER SEES
--------------|--------------------------------------------------|----------------------------------
Empty / new   | "Create the first milestone" + the rule          | the shape + an invitation
Populated     | milestone cards, each with a 4-step tracker      | release history + what's next
In-progress   | current milestone highlighted; current step ring | where the live release actually is
Slipped       | auto-amber on the current step if its target     | a derived, trustworthy slip flag
              | date passed AND it is not done ("late Nw")       |
Loading       | skeleton milestone cards                          | instant structure, no blank spinner
Error         | inline "Couldn't load this project. Retry."      | recoverable, not a dead end
```

Auto-derived slip rule: the "late" flag is computed (a step's target date passed AND the step not done), not PM-entered. The one place v1 shows truth from date math, not typed status. Cheap, high-trust.

Deferred to TODOs (idea-stage scope): responsive behavior per viewport, accessibility (keyboard nav, ARIA landmarks, 44px touch targets, 4.5:1 contrast on body text).

## Engineering Plan (eng review, 2026-06-26)

Locked via /plan-eng-review. These decisions turn the chosen approach (A, thin custom build with the lifecycle-object graft from B) into a buildable spec. Architecture, tests, and performance are settled; the build itself is gated on The Assignment passing.

**Storage realization (decided during /ce-plan, 2026-06-26):** v1 uses **no database**. Each project is a single JSON document in a git data repo, read/written via the provider API; the file's git blob SHA is the optimistic-lock token (D6), and every save is a commit, so git is the change history, audit, and backup (R10). Stack: TypeScript + Next.js (App Router), serverless. Rigidity (D1) is enforced by a shared Zod schema, not DB constraints; "the schema is written" below now means the Zod schema, and "a migration" means a scripted transform over the JSON files. This supersedes the relational-DB framing in the data model and architecture notes below. Full detail: `docs/plans/2026-06-26-001-feat-compass-v1-project-page-plan.md`.

### Locked decisions

- **D1 — Rigidity is schema- AND server-enforced.** Milestone steps (Requirements, Build, Test, Deploy), lifecycle states (NPD, Sustaining, Closed), and the five roles are fixed enums in both the database schema and the server boundary. There is no endpoint to create a milestone type, add a field, or define a role. Rigidity is structural, not a UI convention. Accepted consequence: changing the shape later (e.g. adding a Sign-off step) is a schema migration, not config. That is the point, and it is why the shape must be settled before the schema is written (see Open Questions and The Assignment).
- **D2 — Editing is open (wiki-style) for v1.** Any authenticated employee can edit any project. Chosen deliberately: the team is small and high-trust, and the right role granularity is not yet known (development managers vs developers, for one), so scoping edit rights now would be guessing. This is a two-way door, made safe by D2a/D2b/D6 below, and role-scoped editing can be added later as an additive change because roles are already first-class data.
  - **D2a — Every edit is stamped.** `updated_by` + `updated_at` is written on every write, not just milestone changes. Under open editing the stamp is the only accountability, so it is mandatory and non-skippable.
  - **D2b — Archive, never hard-delete.** Projects and milestones are archived/closed, never destroyed by an ordinary edit. If nothing is ever truly gone, no undo is needed.
- **D5 — Sustaining work is still a milestone.** A maintenance release or hotfix runs the same four steps; the Sustaining lifecycle state is a project-level label, not a different shape. Keeps "nothing happens outside a milestone" and D1 honest, and fits a field-hardware product where even a patch is tested on devices and deployed to the field. If real usage later proves a true escape valve is needed (an N/A step), that is an additive change, deferred.
- **D6 — Optimistic locking on edits.** Concurrent edits to the same project/milestone never silently overwrite each other; the second writer is told the record changed and must reload. This is correctness, not trust: it stops accidental loss of a status update. Everything else stays open, consistent with D2.

### Data model (one JSON document per project)

The entities are unchanged from the original lifecycle-object sketch; only the storage shape differs. Each project is a single self-contained JSON document, so the whole page is one read (this is what moots the old N+1 note). A shared Zod schema is the one shape (D1).

```
data/projects/<id>.json   (in the git data repo)
{
  schemaVersion: 1,
  id, name,
  customerId,                                  // must exist in data/customers.json
  lifecycleStatus: "NPD" | "Sustaining" | "Closed",   // enum (D1)
  roles: { PM, Development, Test, Deploy, CustomerCare },   // fixed keys; person each
  milestones: [
    { id, name, targetDate, actualDate?, releaseUrl?,         // releaseUrl: the release package — SharePoint now, git artifact later
      steps: { Requirements, Build, Test, Deploy },          // fixed keys; each { status, date? }
      updatedBy, updatedAt }
  ],
  docLinks: [ { id, label, url } ],            // raw SharePoint URLs, rendered as links
  archived: false,                             // archive, never hard-delete (D2b)
  updatedBy, updatedAt                          // last-edit stamp (D2a)
}

data/customers.json  ->  [ { id, name } ]      // admin-maintained
```

Fixed-key objects for roles and steps make the rigid set structural (you cannot add a sixth role). Concurrency uses the file's git blob SHA, not a row_version. Deferred, modeled-adjacent (phase 2): per-milestone scope items, test results, deployment records — additive.

### Edit + derive flow (edit a step, re-derive slip)

```
edit a step (status / date)  →  Server Action  ("use server"; a PUBLIC endpoint)
        │
        ▼
  await auth() ──(none)──▶ reject (unauthorized)                            [R9]
        │
        ▼
  Zod parse (strictObject) ──(invalid / extra field)──▶ field errors, no write  [D1]
        │
        ▼
  write file with expected blob SHA ──(stale)──▶ 409 "reload, someone changed this"  [D6]
        │ (fresh; commit author = Entra user)                              [D2a/R10]
        ▼
  stamp updatedBy / updatedAt; archive sets a flag, never deletes          [D2a/D2b]
        │
        ▼
  derive slip (NOT stored): late = target date passed AND status != done   [R6]
        │
        ▼
  return new SHA → page shows derived "late Nw" badge (the only un-fakeable signal)
```

### Architecture notes

- **Boring by default.** TypeScript + Next.js (App Router), deployed serverless. SSO via Entra ID (OIDC, Auth.js v5, JWT sessions — no DB). Data is per-project JSON in a git data repo via the provider API; there is no database. One rule worth holding: Compass tracks releases, it is not the build/deploy system. It links to and records device/release artifacts; it does not own them.
- **Enforcement lives in two places, by design.** A shared Zod `strictObject` schema is the one shape AND every read/write is validated at the server boundary (D1). The schema alone is just types; server validation alone can be bypassed by a hand-edited file. Both — Zod on read (catch drift) and on write (reject bad input) — or rigidity is a fig leaf. Server Actions are public endpoints, so each one re-checks `auth()` and re-validates; `proxy.ts` only redirects, never the authz boundary (CVE-2025-29927).
- **Access model (v1).** Read for any authenticated employee, edit for any authenticated employee (D2). The per-role view is phase 2 and is where the real authorization work lives. Do not build phase-2 authz now.
- **SharePoint is linked, not integrated.** Store and render raw links only. No Graph API, no permission-trimming, no title fetch. If a viewer lacks access, SharePoint's own access-denied handles it.
- **Production failure scenarios.** SSO outage (Entra down): fail to a clear "sign-in unavailable" state, never a white screen. Git-provider outage: writes (and dynamic reads) fail, so write failures must be loud and non-destructive ("couldn't save, your changes are kept, retry") — never silently drop a write. Stale data: with open editing and typed status the page can drift, so the auto-derived slip flag is the trust anchor (it cannot be faked). Concurrent edit: handled by D6 (blob-SHA optimistic lock).

### Performance

- **The old N+1 is mooted by the file model.** One project = one JSON document = one read, so the relational fan-out (Project → Customer → roles → milestones → steps → doclinks) no longer applies. The new performance watch is the **git provider API**: every read/write is a network round-trip with secondary rate limits (~80 writes/min, ~500 writes/hour). Mitigations: one commit per explicit Save (no per-keystroke autosave), and read-caching (Next `cacheComponents` + `updateTag`, or a KV store) as the first scale lever and outage-resilience step. v1 reads are dynamic.

## Open Questions

Resolved or re-scoped by this review:

- **Sign-off step — now BLOCKING for the schema.** Folded into Requirements for now, but under D1 adding a fifth step later is a migration. Resolve it as an output of The Assignment (does the real project actually have a sign-off gate people wait on?) BEFORE the schema is frozen. This is the one shape question that must close before E1.
- **Sustaining model — resolved (D5).** Sustaining is a lifecycle label; maintenance releases are ordinary 4-step milestones. No separate shape.
- **Edit permissions — resolved for v1 (D2), revisit later.** Open editing now; role-scoped editing is additive once the role granularity (e.g. dev-manager vs developer) is known.

Still open:

- **Customer list source + owner — on the critical path.** A project cannot be created without a valid customer (test 4). v1 can start with a manually maintained admin list; name an owner before the first real project. Confirm later whether it syncs from a CRM.
- **Responsible roles — complete set?** Are PM / Development / Test / Deploy / Customer Care the full fixed set, or is there (say) a separate Hardware owner? This also feeds the eventual edit-permission model.
- **First non-manager champion?** Without a named PM or dev who will live in it, v1 risks being a manager dashboard. The Assignment is how you find (or fail to find) this person.

Flagged by the outside-voice review (strategy, beyond eng scope, surfaced for the record):

- **Build vs. validate (sequencing).** The doc's own demand section says "don't build yet" (sponsor-driven, no IC champion), and D1 makes the standard permanent before the methodology is settled. Resolution: the build is gated on The Assignment. The Assignment is the kill gate; architecture is locked and ready, but no schema is written until it greenlights the shape. A 2-week Power Apps pilot (Approach C) remains the cheaper adoption test if you want to de-risk further before any custom build.
- **SharePoint reframe.** "Retire SharePoint" means retire it as the place you go to understand a project's status and find its docs (the navigation/index layer). - **Typography as adoption lever — hypothesis, not evidence.** Keep the distinctive typeface (cheap), but treat font licensing as a real dependency and do not over-invest before The Assignment.
- **Accessibility / responsive deferral — risk flag.** This is a company-wide internal tool, so keyboard nav, contrast, and basic responsive matter more than for a niche app. Keep deferred for v1, but build on semantic HTML so a11y is additive, not a retrofit.

## Success Criteria

- Every active project has a Compass page in the standard shape: a customer, named responsible roles, and a stream of milestones. No project lives only in email, SharePoint, and people's heads.
- A developer can find every spec and doc for a project from one page, without asking the PM.
- Anyone can tell, from the page, who owns each function and where the current release actually is.
- A PM assembles project status from the page instead of building a status slide by hand.
- Adoption signal: at least one PM and one developer choose to use it for a real project without being forced, and would be annoyed if it disappeared.

## Dependencies

- SSO and identity: Microsoft Entra ID (OIDC), given the M365 tenant. v1 access model: read for any authenticated employee, edit restricted to the PM (and EM). The "dedicated view per role" vision is NOT in v1, it is phase 2, and it is where the real authorization work lives. v1 is one project page that everyone can read.
- SharePoint document linking. v1 decision: store and render raw links only, as-is. No permission checking, no per-viewer trimming, no Microsoft Graph integration. If a viewer lacks access to a linked doc, SharePoint's own access-denied handles it. Richer integration (doc titles, thumbnails, permission-trimmed previews) needs Graph API auth and is explicitly deferred.
- The predefined Customer list: needs a source and an owner. v1 can start with a manually maintained list; confirm whether it should later sync from a CRM.
